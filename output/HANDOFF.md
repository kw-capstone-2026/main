## 0. 먼저 읽을 것 (3줄 요약 + 주의 2가지)

- 저장된 모델로 **2024년 서울 상권×업종 87,179개**의 위험지수(0~100점)와 위험한 이유 Top5를 계산해 파일로 만들었음.
- 계산한 성능은 6월 팀 리포트와 **소수 셋째 자리까지 똑같음** (ROC-AUC 0.909). 계산은 제대로 재현된 것임.
- 시연은 **2024년 4분기(20244) 21,664개 블록**을 DB에 넣어서 보여주면 됨.

**확정된 것 (2026-10-20, PM)**

| 항목 | 확정 내용 | 근거 |
|---|---|---|
| 작품 명칭 | **상권 과포화 위험 진단** | 주의 1 |
| 위험등급 | **위험 75~100점 / 주의 50~74점 / 안전 0~49점** | `risk_grade_calibration.md` (4장 요약) |
| 시연 블록 | 경리단길북측 · 커피-음료 (위험 80점) / 연남동(홍대) · 커피-음료 (주의 57점) / 성수역 · 커피-음료 (안전 19점) | `demo_final_blocks.csv` (2-5) |
| 라벨 | 바꾸지 않음 | 주의 1 |
| 사용 모델 | **모델 A 하나로 통일** (`ml-server/`의 XGBoost+LightGBM, 6월 리포트 모델). 시연·DB·포스터 숫자는 모두 이 모델 기준 | 7장 이상한 점 7 |

**주의 1: "폐업 예측"이라고 말하면 위험함.** 정답(과포화_위험_여부)이 "이번 분기에 폐업이 많았고 매출이 낮은 곳"과 거의 같음. 그리고 모델의 1위 변수가 **이번 분기 폐업 수**로 계산돼 있음 (자세한 근거: `label_check.md`). 그래서 이 모델은 미래 예측보다 **"이번 분기 과포화 상태 진단"**에 가까움. 그래서 **작품 명칭을 "상권 과포화 위험 진단"으로 확정함.** 라벨 정의는 바꾸지 않음. "이번 분기에 과포화 상태인가"라는 진단 목적과 지금 라벨이 정확히 맞기 때문임. 라벨을 바꾸면 모델 재학습이 필요하고 팀 리포트 수치가 전부 바뀌어 포스터 일정(10/31)에 위험함. 라벨을 만든 코드는 저장소에 없음. 폐업 관련 변수를 빼고 다시 학습하면 성능이 크게 떨어짐(ROC-AUC 0.909 → 0.735). 그래서 "진단"이 정확한 표현임 (`ablation_no_closure.md`).

**주의 2: 시연 사례는 일부러 "맞힌 것"을 골랐음.** 시연 후보는 고위험이면 실제 정답=1, 저위험이면 정답=0인 블록을 우선으로 골랐음. 이건 **설명하기 좋게 고른 시연용 선택일 뿐이고, 모델이 전부 맞힌다는 뜻이 아님.** 실제로는 위험 등급(75점 이상) 블록 4개 중 1개 정도만 진짜 과포화임 (24.9%). 확률 0.5 기준으로는 7개 중 1개 (정밀도 13.7%).

## 1. 무엇을 계산했는지

모델은 2019~2023년 데이터로만 학습했음. 그래서 2024년은 모델이 **학습 때 한 번도 보지 못한 데이터(시험 구간)**임. 이 2024년 1~4분기 87,179개 블록(상권 하나 × 업종 하나 × 분기)에 저장된 두 모델(XGBoost, LightGBM)을 적용함. 각 블록의 "과포화 위험 확률"은 두 모델 확률을 0.3 : 0.7로 섞어서 구함. 이 확률을 0~100점 **위험지수**로 바꾸고, 블록마다 점수에 가장 크게 영향을 준 변수 5개(**SHAP Top5**)를 뽑음. 시연 때는 모델을 다시 돌리지 않고 이 결과를 DB에서 읽기만 함.

### 용어 풀이

| 용어 | 쉬운 설명 |
|---|---|
| 블록 | 상권 하나 × 업종 하나. 예: "경리단길북측의 커피-음료". DB 한 줄 |
| 확률 (prob) | 모델이 본 "과포화 위험일 가능성" 0~1. 실제 확률보다 높게 나오는 경향 있음 (3장) |
| 위험지수 (risk_score) | 확률을 0~100점으로 바꾼 값. 50점 = 확률 0.5, 70점 ≈ 0.79, 80점 ≈ 0.88 |
| 위험등급 | 위험지수를 나눈 것. **위험 75~100 / 주의 50~74 / 안전 0~49 (확정)** |
| SHAP | 이 블록의 점수가 왜 이렇게 나왔는지 변수별로 나눈 값. **+면 위험을 올린 이유, −면 낮춘 이유** |
| ROC-AUC | 위험 블록을 안전 블록보다 높게 줄 세우는 능력. 0.5 = 찍기, 1.0 = 완벽 |
| 정밀도 | 모델이 "위험"이라 한 것 중 진짜 위험인 비율 |
| 재현율 | 진짜 위험 중 모델이 "위험"이라고 잡아낸 비율 |

위험지수 공식: p를 0.0001~0.9999로 자른 뒤 `risk_score = round(clip(50 + 15 × ln(p/(1−p)), 0, 100))`

### 3-2. 믿어도 되는 것

- 계산 자체: 팀 리포트 수치를 그대로 재현했고, 처음부터 두 번 실행해도 결과 파일이 똑같음.

- 실제 위험 블록의 84%를 "위험"으로 잡아낸다는 것 (재현율).

### 3-3. 한계 (과장하지 말 것)

- **확률이 높게 나옴:** 학습 때 위험 클래스에 약 33배 가중치를 줬음. 그래서 실제 위험은 3.1%인데, 확률 0.5 이상이 19.0%임. "폐업 확률 88%" 같은 말은 쓰지 말고, 점수·순위로만 말할 것.
- **정밀도가 낮음 (13.7%):** "위험"으로 나온 블록 7개 중 1개 정도만 진짜 위험임. 놓치지 않는 쪽으로 맞춘 모델임.
- **SHAP은 XGBoost 기준:** 점수는 앙상블 값이고, 이유는 XGBoost만 설명함. 두 모델의 성능이 거의 같아서(0.9076 / 0.9089) 경향은 비슷함.
- **한 변수에 크게 의존함:** `전년_동기_대비_폐업_증감률`이 전체 SHAP의 37.8% (XGBoost 자체 중요도로는 61.9%)를 차지함. 20244 블록의 70.9%에서 이유 1위이고, 100% Top5에 들어감. 그래서 시연에서 이유가 대부분 비슷하게 보일 수 있음.
- **누수 가능성 (주의 1):** 위 변수는 **이번 분기 폐업 수**로 계산됨 (재계산 일치율 100%). 정답=1 블록은 100% 이번 분기에 폐업이 있었음. 이번 분기 폐업률 하나만으로 정답을 맞히는 정도가 ROC-AUC 0.918로, 모델(0.909)보다 높음. → `label_check.md`
- **폐업 변수를 빼면 성능이 크게 떨어짐:** 폐업 관련 변수 3개를 빼고 같은 설정으로 다시 학습하면 ROC-AUC 0.909 → 0.735, PR-AUC 0.317 → 0.094가 됨. 그래도 무작위보다는 확실히 나음 (4분기 위험 등급의 실제 과포화 비율이 평균의 4.0배). 즉 매출·점포 구조만으로도 신호가 있고, 폐업 지표가 진단 정확도를 크게 올려 줌. → `ablation_no_closure.md`
- **상권 단위 변수가 많음:** 32개 변수 중 23개는 같은 상권이면 업종이 달라도 값이 같음. 같은 상권 안 업종 간 차이는 9개 변수(매출, 전년 대비 폐업 증감 등)로만 만들어짐.

## 4. 확정된 결정 (팀 결정 원문 그대로)

1. 예측 단위는 "상권 × 업종". DB의 한 줄(블록) = 상권 하나 × 업종 하나.
2. 위험등급(위험/주의/안전) 기준은 시연 중심으로 정한다. 점수 분포를 보고, 시연용 상권 3곳이 고위험·중간·저위험으로 나뉘어 보이도록 조정. 임시 시안: 70점 이상 위험 / 40~70 주의 / 40 미만 안전. 기준값은 스크립트 맨 위 상수로 두어 쉽게 바꿀 수 있게 할 것. (이번 작업에서는 임시 등급 열만 만들고 최종 확정은 하지 않는다.)
3. 옛 설계 항목(생존곡선 survival_curve, 6개월 생존확률 survival_6m, 안전지수 csi_score)은 만들지 않는다.

**→ 2번 결정에 따라 2026-10-20에 등급 기준을 확정함: 위험 75~100 / 주의 50~74 / 안전 0~49** (자세한 근거: `risk_grade_calibration.md`)

정한 방법 (신용평가 등급표와 같은 방식):
- 2024년 1~3분기 블록을 5점 단위로 나누고, 구간마다 실제 과포화 비율이 평균의 몇 배인지 계산함.
- **50점**: 실제 과포화 비율이 평균을 넘기 시작하는 점수 (45~49점 0.98배 → 50~54점 1.40배). 모델의 위험 판정 경계(확률 약 0.5)와도 같음.
- **75점**: 평균의 5배를 넘는 점수 (70~74점 3.2배 → 75~79점 5.1배로 크게 뜀).
- 4분기(시연 분기)는 기준을 정할 때 쓰지 않고 검증에만 씀.

2024년 4분기 검증 결과:

| 등급 | 점수 | 블록 비율 | 실제 과포화 비율 (95% 신뢰구간) | 평균 대비 |
|---|---|---:|---:|---:|
| 위험 | 75~100 | 6.0% | 24.9% (22.6~27.4%) | 9.9배 |
| 주의 | 50~74 | 11.9% | 5.8% (5.0~6.8%) | 2.3배 |
| 안전 | 0~49 | 82.1% | 0.4% (0.3~0.5%) | 0.2배 |

- 등급 사이의 신뢰구간이 겹치지 않음 → 세 등급이 통계적으로 확실히 구분됨.
- 실제 과포화 블록의 86.1%가 주의 이상으로 분류됨.
- 위험지수 분포 (2024년 전체): 최소 0, 하위 10% 6점, 25% 15점, 중앙값 26점, 상위 25% 42점, 상위 10% 68점, 상위 5% 77점, 최대 100점

  - 예: `3110084_CS100010`, `경리단길북측 · 커피-음료`, `골목상권`, `커피-음료`, `37.5417370`, `126.9913598`, ,
- **predictions.csv** (21,664행): `block_id`, `risk_score`, `risk_grade`, `closure_rate`, `open_rate`, `survival_6m`(빈칸)
- **shap_features.csv** (108,320행 = 블록 × 5): `block_id`, `rank`, `name`, `shap_value`, `label`
  - 재료: `shap_top5_2024_q4.csv`. 상권_코드 + "_" + 서비스_업종_코드로 bas_id를 만들어 연결함
- **industry_stats.csv**: `block_id`, `industry_name`, `store_count`, `ratio`, `avg_operating_months`(⚠ 위 표 참고), `recorded_at`
  - 블록이 속한 상권에서 `점포_수_x`가 많은 업종 상위 5개
  - 같은 상권의 블록들은 같은 5줄을 가짐 → 최대 약 108,000행
- **survival_curve.csv는 만들지 않음**
- **DB 적재 순서: blocks → predictions → shap_features → industry_stats**

#### block_id 연결 방법

blocks.id는 DB가 자동으로 매기는 번호라서 CSV를 만들 때는 알 수 없음. 둘 중 하나를 고를 것:
1. **(추천)** blocks를 먼저 넣고 `SELECT id, bas_id FROM blocks`로 번호표를 받은 뒤, 나머지 CSV의 block_id를 채움
2. blocks.csv에 `id`를 1부터 직접 넣음. 빈 DB에서만 가능하고, 넣은 뒤 `SELECT setval('blocks_id_seq', (SELECT max(id) FROM blocks));` 실행 필요

#### 프론트·백엔드 담당에게 전달할 것 (프론트 목업 가이드 기준)

- 목업은 `block.csi` 값(8.0 기준)으로 안전/위험 화면을 나눔. csi는 만들지 않으므로 **risk_score 또는 risk_grade 기준으로 바꿔야 함**.
- 목업 등급 텍스트는 '낮음'/'높음'임. DB 값(위험/주의/안전)에 맞춰야 함.
- SHAP 색은 `shapValue >= 0 ? 빨강 : 파랑` 방식이라 우리 데이터(+/−)와 그대로 맞음.
- 목업에 6개월 생존확률·생존곡선 화면이 있음. 데이터가 없으므로 숨겨야 함.
- 한 상권의 업종 블록들이 지도에서 같은 좌표에 겹침 (상권당 업종 중앙값 11개). 추천: "업종 선택 → 상권 마커 색이 그 업종의 위험도로 바뀜" 방식.

#### 백엔드 API가 이 데이터로 실제 어떻게 동작하는지 (`origin/feature/backend-api` 코드 기준)

| API | 이 데이터로 동작 | 해야 할 것 |
|---|---|---|

| `GET .../shap` | 정상 동작 (블록당 5개, rank 순) | 부호로 색 구분 (지금 방식 그대로) |
| `GET .../survival-curve` | 데이터가 없어서 **에러(404, PREDICTION_NOT_FOUND)를 냄** | 프론트에서 **호출하지 않기** (생존곡선 영역 삭제) |

## 7. 이상한 점, 가정, 결정 현황

### 이상한 점

1. **라벨·누수:** 정답이 "이번 분기 폐업률 > 2.5% 그리고 가게당 매출이 낮음" 규칙과 거의 같음 (단순 규칙 ROC-AUC 0.946). 모델 1위 변수가 이번 분기 폐업 수를 씀 → `label_check.md`. 문서마다 라벨 설명도 다름 ("개업 2년 내 폐업" vs "매출 하락 및 폐업률 기반").
2. `_y` 열, `운영_영업_개월_평균`, `상권 내부 업종 점유율(%)`은 같은 상권·분기 안에서 100% 같은 값임. 상권 평균과 비슷하지만(상관 0.79) 정확한 계산식은 확인 못 함.
3. 좌표가 상권 단위라서 한 상권의 업종 블록들이 지도에서 겹침.
4. `폐업_률_x` 최댓값이 125임 (% 단위인데 100을 넘음). 이상치로 보임.
5. 저위험 블록은 0점이 많음 (확률 약 0.036 이하는 모두 0점). 시연에서는 10~20점대 블록이 자연스러움.
6. 루트의 README는 초기 구상(점포 단위 생존 기간 + POI)이라 지금 모델과 맞지 않음. 이번 작업은 지시대로 6월 분류 모델·현재 코드를 기준으로 함.
7. **팀 안에 다른 실험 모델(모델 B)이 있었음 → 모델 A로 통일하기로 결정함 (2026-10-22).**

| | 모델 A: 이 문서의 모델 (`ml-server/`, 6월 리포트, **시연에 씀**) | 모델 B: 시각화 팀원 작업 (`visualization` 브랜치, `gemini.md/team)visualiation/`) |
|---|---|---|
| 정답 | `과포화_위험_여부` (2024년 3.1%) | `폐업발생` = 이번 분기 폐업 점포 수 > 0 (23%) |
| 폐업에서 나온 변수 | 사용함 (`전년_동기_대비_폐업_증감률`, `폐업_률_y` 등) | 누수라서 **뺐음** |
| 성능 (2024년) | ROC-AUC 0.909 / PR-AUC 0.317 | ROC-AUC 0.808 / PR-AUC 0.627 |
| 가장 큰 단서 | 작년 대비 폐업 증감 (SHAP 비중 38%) | 이번 분기 개업 점포 수 (중요도 57%) |

- 두 모델은 묻는 질문(정답)이 달라서 숫자를 나란히 비교하면 안 됨. 두 모델 성능은 같은 데이터로 다시 계산해서 확인함. 모델 B는 "가게가 많은 곳일수록 이번 분기에 폐업이 한 건이라도 나온다"는 규모 효과가 큼 (점포 수 하나만으로 ROC-AUC 0.74).
- **시연·DB·포스터는 모두 모델 A 숫자만 씀.** 모델 B의 성능 그림·숫자는 쓰지 않음.
- 모델 B 발표 가이드의 Q&A "폐업에서 파생된 변수는 피처에서 제외했다"는 모델 A와 맞지 않으므로 쓰지 않음. 누수 질문에는 `ablation_no_closure.md` 결과로 답함.
- 모델 B 폴더의 데이터 설명 그림(클래스 비율, 시간 분할 이유 등)은 모델 성능과 상관없는 데이터 그림이라 필요하면 쓸 수 있음. 단, 그림 속 정답이 "폐업 발생"인지 "과포화"인지 확인하고 쓸 것.
