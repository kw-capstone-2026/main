# 상권 과포화 위험 진단

공공데이터와 머신러닝으로 서울 상권×업종의 이번 분기 과포화 위험을 진단하고, 위험한 이유까지 설명하는 서비스.

- 2026 캡스톤디자인, 광운대학교 정보융합학부
- 팀 "이음": 김지우, 백지윤, 이민재, 장은지, 정현주
- 지도교수: 이상민 교수님
- 웹 서비스: https://csi-platform.vercel.app/map (블록 상세 데이터는 백엔드를 로컬에서 실행해야 표시됨)

---

## 프로젝트 개요

같은 업종이라도 어느 상권에 있느냐에 따라 경쟁과 폐업 흐름은 크게 다름. 창업을 준비하는 사람이 상권별 과포화 정도를 객관적으로 비교할 수 있도록 아래 세 가지를 목표로 함.

1. 상권×업종 블록마다 이번 분기 과포화 위험을 0~100점으로 진단
2. 위험을 올리거나 낮춘 이유 5가지를 함께 제시 (SHAP)
3. 지도에서 위험 · 주의 · 안전 등급으로 한눈에 비교

미래 폐업을 맞히는 모델이 아니라, 이번 분기 데이터로 지금의 과포화 상태를 진단하는 모델임.

## 데이터

| 항목 | 내용 |
| --- | --- |
| 기간 | 2019~2024년, 24개 분기 |
| 규모 | 512,626행 (상권 1,570곳, 업종 62개) |
| 입력 변수 | 32개 (매출·수요 7, 점포·개폐업 7, 경쟁 구조 10, 배후지·입지 8) |
| 정답 | 과포화 위험 여부 (상권×업종×분기), 2024년 기준 3.1% |
| 학습 / 시험 | 학습 2019~2023년 (20개 분기), 시험 2024년 (87,179블록, 학습에 쓰지 않음) |

데이터 출처: 서울 열린데이터광장, 서울시 상권분석서비스 (추정매출, 점포, 유동인구, 직장인구, 아파트, 소득소비, 집객시설 등 상권 단위 데이터)

## 분석 방법

1. 데이터 결합: 상권×업종×분기 블록 단위로 32개 변수 구성
2. 모델 학습: XGBoost, LightGBM (위험 클래스에 약 33배 가중치)
3. 앙상블: 두 모델 확률을 0.3 : 0.7로 결합
4. 위험지수: `위험지수 = 50 + 15 × ln(p / (1 − p))`, 0~100점으로 제한. 50점이 판정 경계(p = 0.5)
5. 위험 이유: XGBoost 기준 SHAP으로 블록별 Top5 계산

위험 등급은 2024년 1~3분기로 기준을 정하고 4분기로 검증함.

| 등급 | 점수 | 블록 비율 | 실제 과포화 비율 | 평균 대비 |
| --- | --- | ---: | ---: | ---: |
| 위험 | 75~100 | 6.0% | 24.9% | 9.9배 |
| 주의 | 50~74 | 11.9% | 5.8% | 2.3배 |
| 안전 | 0~49 | 82.1% | 0.4% | 0.2배 |

(2024년 4분기 기준, 4분기 평균 과포화 비율 2.5%)

## 주요 결과

2024년 시험 데이터 87,179블록, 앙상블 확률 0.5 이상(50점 이상)을 위험으로 판정했을 때의 성능.

| 지표 | 값 |
| --- | ---: |
| ROC-AUC | 0.909 |
| PR-AUC | 0.317 (무작위 기준 0.031) |
| 재현율 | 84.2% |
| 정밀도 | 13.7% |

- 실제 과포화 블록을 놓치지 않는 쪽으로 설계함. 실제 과포화 2,705곳 중 2,277곳을 찾아냄.
- SHAP 비중 1위 요인은 "작년 같은 분기 대비 폐업 증감" (37.8%). 이번 분기 폐업 흐름에 크게 기대는 진단 모델임.

시연 블록 (2024년 4분기, 커피-음료)

| 상권 | 구분 | 위험지수 | 등급 |
| --- | --- | ---: | --- |
| 경리단길북측 | 골목상권 | 80 | 위험 |
| 연남동(홍대) | 발달상권 | 57 | 주의 |

## 시스템 구성

```
AI 분석 결과 (사전 계산)  →  PostgreSQL + PostGIS  ↔  Spring Boot REST API  ↔  React 웹 서비스
위험지수 · 등급 · SHAP        블록 · 진단 결과 · SHAP      Swagger                     지도 · 블록 상세 · 위험 이유
                              :5432                        :8080                       :5174
```

서비스는 미리 계산한 결과를 DB에서 조회만 함. 모델을 실시간으로 돌리지 않음.

| 구분 | 기술 |
| --- | --- |
| 모델 | Python, XGBoost, LightGBM, SHAP |
| DB | PostgreSQL 15 + PostGIS 3.4 (Docker) |
| 백엔드 | Java, Spring Boot 3.5, Spring Data JPA, Swagger |
| 프론트엔드 | React 19, Vite, Leaflet (OpenStreetMap), Recharts |
| 실행 / 배포 | Docker Compose, Vercel |

## 실행 방법

사전 준비: Git, Docker Desktop, Node.js 18 이상

### 1. 백엔드 + DB

```bash
git clone -b feature/backend-api https://github.com/kw-capstone-2026/main.git backend-run
cd backend-run
```

프로젝트 루트에 `.env` 파일을 만들고 아래 항목을 채움. 값은 팀 내부에서 따로 공유함.

```
DB_NAME=
DB_USERNAME=
DB_PASSWORD=
JWT_SECRET=
DOCKER_DB_URL=jdbc:postgresql://db:5432/<DB_NAME>
```

```bash
docker compose up -d --build
```

- 처음 실행할 때 `database/schema.sql`, `seed.sql`, `seed-ai-2024q4.sql.gz` 순서로 자동 적재됨.
- 예전에 만든 DB 볼륨이 있으면 새 데이터가 안 들어가므로 `docker compose down -v` 후 다시 실행.
- 확인: http://localhost:8080/swagger-ui/index.html 에서 `GET /api/v1/blocks/828/prediction` 호출 시 경리단길북측 80점이 나오면 정상.

### 2. 프론트엔드

```bash
git clone -b feature/frontend-components https://github.com/kw-capstone-2026/main.git frontend-run
cd frontend-run
npm install
npm run dev
```

브라우저에서 http://localhost:5174/map 접속. `/api` 요청은 8080 백엔드로 전달됨.

### 3. 위험지수 · SHAP 재계산 (선택)

`XGboost_basic` 브랜치의 `handoff_output/HOW_TO_REPRODUCE.md` 참고.

## 한계 및 향후 과제

- 미래가 아닌 이번 분기 상태를 진단하며, 폐업 관련 변수 의존도가 높음 (폐업 변수 3개를 빼면 ROC-AUC 0.735)
- 위험 클래스 가중치 때문에 모델 확률이 실제보다 높게 나오므로, 확률보다 위험지수와 순위로 해석해야 함
- 향후: 다음 분기 상태를 미리 알려 주는 조기 경보로 확장
