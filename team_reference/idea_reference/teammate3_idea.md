**[Day 2-3] FastAPI 서버 구조 확정 + 간단한 엔드포인트 1개 배포**
저는 FastAPI → Spring Boot Gateway 경유보다는, 프론트가 FastAPI를 직접 호출하는 구조가 현실적이라고 생각합니다. 발표 시연까지 일정이 빠듯하고 SHAP 연산 결과는 ML 서버 내부에서 바로 JSON으로 뱉는 게 레이턴시도 짧고 디버깅도 쉽기 때문입니다.

**[Day 3-4] 캐싱 방식 결정 (A안 vs B안)**

- A안(실시간 연산): 좌표/업종 입력 → 모델 추론 → SHAP 계산 → JSON 반환. 구현은 직관적이지만 SHAP 계산이 느릴 수 있음.
- B안(사전 캐시): 상권 단위로 미리 예측 결과를 계산해 DB나 JSON 파일로 저장해두고 API는 조회만 함. 응답 빠르고 시연 안정성 높음.

→ B안은 상권 수가 수천 개라도 미리 돌려두면 되고, 시연 중 서버 렉 걱정이 없습니다. 다만 업종 조합이 너무 다양하면 A안 부분 병행도 고려할 수 있습니다. 이 부분은 투표로 정하면 좋을 것 같습니다.

**[Day 4-5] 프론트 SHAP 시각화 연동**

- 상단: 위험도 수치(예: 94.76%) + 색상 게이지(빨강/주황/초록)
- 중단: SHAP 기여 요인 가로 막대차트 (긍정 요인 파랑, 부정 요인 빨강)
- 하단: 간단한 해석 문구 ("이 점포는 유동인구 감소와 주변 동종업종 증가가 주요 위험 요인입니다")
  이 정도면 교수님 발표에서 인상적으로 보일 것 같습니다. Recharts나 Chart.js 둘 다 SHAP 바차트 구현은 어렵지 않으니 API 스펙만 먼저 확정되면 빠르게 붙일 수 있습니다.
